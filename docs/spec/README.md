# Специфікація «Maze: Bunker-71» — структура

Нормативне джерело проєкту. Документ `Стратегія_MVP_та_специфікація_v1.2.docx` повністю перенесено
сюди (усі 117 розділів) і заморожено як знімок v1.2 з правками аудиту; далі він не редагується.
Якщо docx і ці файли розходяться, правильні ці файли.

| Файл | Шар | Що всередині |
|---|---|---|
| `01-vision.md` | Бачення та лор | Чому світ такий; що відчуває гравець. Без чисел і правил |
| `02-spec-mvp.md` | Нормативна специфікація MVP | Лише чинні правила, по одному варіанту на правило, у форматі вимоги |
| `03-decisions.md` | Журнал рішень і прототипів | Що було, що стало, чому, який прототип це показав |
| `04-roadmap.md` | Post-MVP | Вимоги етапів EPIC-14…29 у тому самому форматі, але без обов’язкового тесту |

## Формат вимоги

```
### REQ-<ОБЛАСТЬ>-<NN> Назва
- Етап: MVP-N | EPIC-NN
- Правило: одне чинне формулювання, без історії
- Одиниці: розмірності всіх величин у правилі
- Передумови: стани світу, за яких правило діє
- Результат: що змінюється у світі, які події пишуться в журнал
- Винятки: перелічені явно; «немає», якщо їх немає
- Історія: ST-NN.N (беклог 18.3–18.4)
- Рішення: DEC-NNN (посилання в 03-decisions.md)
- Тест: перевірюваний критерій із числами і допуском
```

Правила:

- Вимога має рівно один чинний варіант. Попередні варіанти, прототипи і «чому саме так»
  живуть у `03-decisions.md` і згадуються у вимозі лише через `Рішення: DEC-NNN`.
- Число з’являється в специфікації один раз. Інші вимоги посилаються на ID, а не повторюють число.
- Якщо інший документ каже інакше, правильна `02-spec-mvp.md`; це успадковує правило
  «єдиного джерела істини» з docx §10.4 і §18.7.
- Критерії приймання (docx §18.6) стають похідними: критерій історії = об’єднання полів
  `Тест` усіх вимог з цією історією.
- Області в пілоті: `POP` — популяція заражених, `VENT` — вентиляція. Далі додаються
  `MAZE`, `ARCH`, `COMBAT`, `NEEDS`, `HEALTH`, `CLIMATE`, `ITEMS`, `NPC`, `ECON`, `UI`, `SAVE`.

## Журнал рішень

```
### DEC-NNN Назва
- Дата: рік-місяць (за версією документа)
- Стосується: REQ-…
- Було: попереднє правило
- Стало: чинне правило (лише посилання на REQ, без повторення)
- Чому: аргумент або результат прототипу з числами
- Джерело: docs/proto/…, розділ docx, пункт аудиту
```

## Контракти

`05-contracts.md` — модель світу (ID, власник стану, правила зміни), часовий контракт
(дві шкали, режими годинника, частоти тіків), діаграми станів у Mermaid і порядок обробки
подій (фіксований порядок тіку, черга команд популяції, транзакція защіпки шлюзу). Вимоги
в `02-spec-mvp.md` посилаються на контракти, а не повторюють їх.

## Тести і нефункціональні вимоги

`06-tests.md` — чотири класи перевірок (INV / NUM / STAT / PLAY) з правилами допусків замість
загального «± 5 %», запис тесту, тести пілота, інтеграційні сценарії, правило оцінки прототипів
тією самою метрикою, що в критерії. `07-nfr.md` — стенди, еталонні сцени, бюджети кадру,
перебудови чанка, збереження і повна розкладка керування з протоколами вимірювання.

## План

`08-plan.md` — вимірювання того, які системи встигають проявитися за ран 30–60 і 90–150
ігрових годин, перепланування фаз із фундаментом у фазі 1, вертикальні зрізи VS-1/2/3 з
питаннями плейтесту і порогами, правило проявленості для довгих циклів.

## Беклог

`09-backlog.md` — команда і ритм, MoSCoW, повний беклог MVP (епіки → історії → задачі), таблиця обсягу
історія → етап → залежності, граф залежностей, реєстр підфункцій SF-01…13, прототипи до спринту 1,
ризики. Це джерело істини для обсягу; фази — `08-plan.md`.

## Довідник

`10-appendix.md` — аналіз оригіналу Maze-Rase, порівняння рушіїв і стек, архітектура модулів,
глосарій, зведена таблиця констант оригінал → 3D. Правил не містить.
