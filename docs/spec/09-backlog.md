Джерело істини для обсягу і порядку робіт. Перенесено з docx §17, §18.1, §18.3, §18.5, §18.7–18.9, §19

## A. Команда і ритм

Команда (рішення замовника, v1.2): один розробник, який виконує код, контент (Asset Store, Mixamo, ProBuilder, Blender), баланс і продюсування. Bus factor = 1 — ризик у розділі 19. Підрядники на арт і аудіо розглядаються після MVP.
Kanban-ритм з двотижневим оглядом (Scrum-церемонії для однієї людини надлишкові). Definition of Ready: історія має критерії приймання (18.6), залежності виконані (18.7), для UI-історій є макет (16.10). Definition of Done: код у main через PR із зеленим CI, PlayMode/EditMode-тести на кожен критерій приймання, баланс у JSON, оновлений розділ документа в тому самому PR.
Оцінки — в людино-днях (л/д) на одного розробника, лише код і інтеграція; контент оцінено окремо у 18.2. Сума беклогу MVP: 228 л/д коду + 45 л/д контенту = 273 л/д ≈ 55 робочих тижнів при 5 л/д на тиждень; буфер 15 % → 63 тижні. Story Points у Jira не використовуються.

Правило рецензії (аудит 2.7): для кожної історії фаза кожної залежності ≤ фаза історії, крім
залежностей із позначкою «заглушка» або «прапорець». Перевірка — скрипт `docs/check_scope.py`
(процесний KPI).

## B. MoSCoW

MVP — «вертикальний зріз» одного сектора, у якому працює вся петля гри: прокинутись → шукати ресурси → воювати/уникати → задовольняти потреби → торгувати → відкрити шлюз. Критерій: тестувальник, який не бачив гри, грає 60 хв без інструкцій і може пояснити, від чого помер. Ця таблиця — огляд; етап кожної функції визначає таблиця 18.7, і в разі розбіжності діє 18.7.
